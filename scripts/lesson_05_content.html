2. Topic Communication Architecture & DDS

A Topic is a unidirectional, strongly-typed data bus over which nodes exchange messages. ROS 2's Pub/Sub architecture provides three levels of architectural decoupling:

⏳

Temporal Decoupling

Publishers and subscribers do not need to be active at the same time. A subscriber can join minutes after a publisher starts without causing errors.

🌐

Spatial Decoupling

Nodes do not know each other's IP addresses or process IDs. They address messages exclusively by topic name (e.g., /chatter or /cmd_vel).

⚡

Synchronization Decoupling

Publishing is non-blocking. A publisher does not wait for subscribers to receive or process data, preventing sensor loops from stalling.

Use the interactive architecture canvas below to explore how data packets serialize, travel across DDS middleware, and trigger event callbacks in real time.

💡 DDS (Data Distribution Service) Under the Hood

ROS 2 completely eliminates the centralized ROS 1 master (roscore). Instead, it relies on industrial OMG DDS / RTPS middleware (such as CycloneDDS or Fast-DDS). Nodes use peer-to-peer multicast discovery to detect compatible publishers and subscribers automatically.

python
#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class MinimalPublisher(Node):
    def __init__(self):
        # 1. Initialize base class with unique node name
        super().__init__('minimal_publisher')

        # 2. Create publisher on 'chatter' with QoS queue depth 10
        self.publisher_ = self.create_publisher(String, 'chatter', 10)

        # 3. Create a non-blocking 2.0 Hz timer (period = 0.5 seconds)
        timer_period = 0.5
        self.timer = self.create_timer(timer_period, self.timer_callback)

        # 4. Message counter
        self.i = 0
        self.get_logger().info('MinimalPublisher node initialized. Publishing to "/chatter" at 2 Hz...')

    def timer_callback(self):
        msg = String()
        msg.data = f'Hello ROS 2: {self.i}'
        self.publisher_.publish(msg)
        self.get_logger().info(f'Publishing: "{msg.data}"')
        self.i += 1


def main(args=None):
    # Initialize the ROS 2 Python client library
    rclpy.init(args=args)

    # Instantiate the node
    minimal_publisher = MinimalPublisher()

    # Spin the node so timer callbacks execute
    try:
        rclpy.spin(minimal_publisher)
    except KeyboardInterrupt:
        pass
    finally:
        minimal_publisher.destroy_node()
        rclpy.shutdown()


if __name__ == '__main__':
    main()

Line-by-Line Code Breakdown

  1. from rclpy.node import Node: Standard object-oriented pattern. All ROS 2 Python nodes inherit from Node to access logging, timers, parameters, and communication interfaces.
  2. super().__init__('minimal_publisher'): Assigns the node name on the computational graph. When you run ros2 node list, this is the name displayed.
  3. self.create_publisher(String, 'chatter', 10):
    • String: The message interface type from std_msgs.msg.
    • 'chatter': The topic name. (Relative names automatically resolve to /chatter under the root namespace).
    • 10: The QoS history depth (queue size). If the system experiences a momentary network delay, DDS buffers up to 10 unread messages in memory before dropping older ones.
  4. self.create_timer(0.5, self.timer_callback): Schedules a periodic callback running at 2 Hz (1.0 / 0.5 = 2.0 Hz). Never use blocking Python while True: time.sleep() in ROS 2; timers run cooperatively within the single-threaded executor.
  5. rclpy.spin(minimal_publisher): Enters a non-terminating event loop that listens for timer expirations, DDS message arrivals, and system signals.

5. Writing the Subscriber Node & Multi-Node Execution

Now let's build the receiving node: listener.py. Create ~/ros2_ws/src/navpro_basics/navpro_basics/listener.py:

python
#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class MinimalSubscriber(Node):
    def __init__(self):
        super().__init__('minimal_subscriber')

        # Create subscription on topic 'chatter'
        self.subscription = self.create_subscription(
            String,
            'chatter',
            self.listener_callback,
            10
        )
        self.subscription  # Prevent unused variable warning

        self.get_logger().info('MinimalSubscriber node initialized. Listening to "/chatter"...')

    def listener_callback(self, msg):
        """
        Executed automatically whenever a new String message arrives on '/chatter'.
        """
        self.get_logger().info(f'I heard: "{msg.data}"')


def main(args=None):
    rclpy.init(args=args)
    minimal_subscriber = MinimalSubscriber()

    try:
        rclpy.spin(minimal_subscriber)
    except KeyboardInterrupt:
        pass
    finally:
        minimal_subscriber.destroy_node()
        rclpy.shutdown()


if __name__ == '__main__':
    main()

6. Developer Superpower: The --symlink-install Build Mode

In standard C++ development, every code edit requires recompiling machine binaries. However, Python is an interpreted scripting language. By default, colcon build copies your Python scripts from src/ into the install/ directory. If you change a line of code in talker.py, your edits will not run until you re-execute colcon build.

To eliminate this repetitive build cycle, ROS 2 provides the --symlink-install flag:

bash
cd ~/ros2_ws
colcon build --symlink-install --packages-select navpro_basics
source install/setup.bash

Standard Build (Default)

Copies Python files from src/ into install/. Requires running colcon build after every single code edit.

Symlink Install (--symlink-install)

Creates Linux symbolic links from install/ pointing directly back to your source files in src/. Edit your code in VS Code, save, and rerun immediately!

⚠️ The Golden Rule of --symlink-install

While Python source changes are reflected instantly, you MUST still re-run colcon build whenever you:

  1. Add or modify an entry point in setup.py.
  2. Add a new dependency to package.xml.
  3. Add new launch files or YAML config files.

7. Quality of Service (QoS) Deep Dive

Unlike ROS 1 (which used raw TCP sockets with default settings), ROS 2 allows developers to fine-tune transport behavior per topic using DDS QoS Profiles. Real robots operate in environments where network bandwidth, latency, and reliability vary dramatically.

QoS Policy Settings Behavior & Robotics Use Case
Reliability RELIABLE
BEST_EFFORT		 RELIABLE: Guarantees delivery via packet acknowledgments and retransmission (like TCP). Used for state machines, e-stop, and navigation goals.
BEST_EFFORT: Drops packets if delayed, minimal latency (like UDP). Essential for high-rate sensor streams (30 Hz cameras, 10 Hz LiDAR).
Durability VOLATILE
TRANSIENT_LOCAL		 VOLATILE: Messages are not retained. Late-joining subscribers only receive messages published after they connect.
TRANSIENT_LOCAL: "Latched" topic. The publisher keeps the last N messages in memory so late-joining nodes immediately receive critical data (e.g., /map or robot footprint).
History & Depth KEEP_LAST (N)
KEEP_ALL		 KEEP_LAST: Maintains a ring buffer of size N in memory. Older messages are discarded when the buffer is full.
KEEP_ALL: Buffers all messages until delivered (can cause unbounded memory consumption if subscriber hangs).

7.1 The QoS Compatibility Rule (Rx ≤ Tx)

In ROS 2, a publisher and subscriber will only connect if their QoS profiles are compatible. The general rule is "Requested ≤ Offered" (Rx ≤ Tx): a subscriber cannot demand a higher guarantee of service than the publisher is offering.

Publisher Offers (Tx) Subscriber Requests (Rx) Connection Compatible?
RELIABLE RELIABLE Compatible ✅ (Data delivered reliably)
RELIABLE BEST_EFFORT Compatible ✅ (Subscriber accepts best-effort delivery)
BEST_EFFORT RELIABLE INCOMPATIBLE ❌ (Silent Failure) — No data will ever be delivered!
BEST_EFFORT BEST_EFFORT Compatible ✅ (Low-latency stream)

7.2 Implementing Custom QoS in Python

ROS 2 provides convenient pre-built profiles in rclpy.qos:

python
from rclpy.qos import QoSProfile, ReliabilityPolicy, DurabilityPolicy, qos_profile_sensor_data

# Option A: Use standard sensor profile (Best-effort, Volatile, Depth 5)
self.lidar_sub = self.create_subscription(
    LaserScan,
    '/scan',
    self.scan_callback,
    qos_profile=qos_profile_sensor_data
)

# Option B: Author a custom mission-critical profile
custom_qos = QoSProfile(
    reliability=ReliabilityPolicy.RELIABLE,
    durability=DurabilityPolicy.TRANSIENT_LOCAL,
    depth=1
)
self.map_sub = self.create_subscription(
    OccupancyGrid,
    '/map',
    self.map_callback,
    qos_profile=custom_qos
)

📐 Kinematic Geometry of a Square

To drive a robot in a square, cycle between two alternating states:

  1. State 0: Drive Straight — Set linear.x = 2.0 m/s, angular.z = 0.0 for 2.0 seconds (travels 4.0 meters).
  2. State 1: Turn 90° Left — Set linear.x = 0.0 m/s, angular.z = 1.5708 rad/s (π/2 rad/s = 90°/s) for 1.0 second (turns exactly 90°).
  3. Repeat continuously across all four sides!

python (Reference Solution)
#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Twist


class TurtleSquareController(Node):
    STATE_FORWARD = 0
    STATE_TURN = 1

    def __init__(self):
        super().__init__('turtle_square_controller')
        self.get_logger().info('Initializing TurtleSquareController...')

        # 1. Create Publisher on '/turtle1/cmd_vel' with Twist and depth 10
        self.cmd_vel_pub = self.create_publisher(Twist, '/turtle1/cmd_vel', 10)

        # State tracking
        self.state = self.STATE_FORWARD
        self.state_elapsed_time = 0.0

        # Durations (seconds)
        self.forward_duration = 2.0
        self.turn_duration = 1.0

        # Velocities
        self.linear_speed = 2.0
        self.angular_speed = 1.5708  # 90 degrees per second (pi / 2)

        # 2. 10 Hz Control Loop Timer (period = 0.1s)
        self.timer_period = 0.1
        self.timer = self.create_timer(self.timer_period, self.timer_callback)

        self.side_count = 0
        self.get_logger().info('TurtleSquareController running! Driving side 1 of square...')

    def timer_callback(self):
        self.state_elapsed_time += self.timer_period
        cmd = Twist()

        if self.state == self.STATE_FORWARD:
            # Drive straight
            cmd.linear.x = self.linear_speed
            cmd.angular.z = 0.0

            if self.state_elapsed_time >= self.forward_duration:
                self.side_count += 1
                self.get_logger().info(f'Side {self.side_count} complete. Turning 90 degrees...')
                self.state = self.STATE_TURN
                self.state_elapsed_time = 0.0

        elif self.state == self.STATE_TURN:
            # Turn 90 degrees
            cmd.linear.x = 0.0
            cmd.angular.z = self.angular_speed

            if self.state_elapsed_time >= self.turn_duration:
                self.get_logger().info('Turn complete. Driving next side...')
                self.state = self.STATE_FORWARD
                self.state_elapsed_time = 0.0

        # Publish command to Turtlesim
        self.cmd_vel_pub.publish(cmd)


def main(args=None):
    rclpy.init(args=args)
    node = TurtleSquareController()

    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        stop_cmd = Twist()
        node.cmd_vel_pub.publish(stop_cmd)
        node.destroy_node()
        rclpy.shutdown()


if __name__ == '__main__':
    main()
